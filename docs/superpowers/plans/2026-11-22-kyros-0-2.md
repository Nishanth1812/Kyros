# Kyros 0.2 Implementation Plan

> **For agentic workers:** Use `superpowers:executing-plans` to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver Kyros 0.2 as a local-first Android release for managing categorized transactions and reviewing balances and spending summaries.

**Architecture:** Keep SQLite as the single source of transaction and category data. Add a transactional v1-to-v2 migration, extend the existing storage and context patterns for category-aware transaction changes, and derive filters and dashboard totals from the loaded records with integer-safe calculations. Reuse React Native controls and existing navigation; add no dependency.

**Tech Stack:** React Native 0.88, TypeScript 6, React Navigation bottom tabs, Android SQLite module, Bun tests, Gradle, GitHub Actions.

**Spec:** [`plan.md`](../../../plan.md), release 0.2.

## Global Constraints

- Android remains the supported platform; minimum Android version remains 7.0 (API 24).
- The release remains local-first and works offline; no account, network service, or backend is added.
- 0.2 adds no HTTP APIs. When future connected features add APIs, use unversioned route paths and maintain compatibility through additive changes and explicit migrations.
- Currency remains INR; amounts remain integer paise and use the existing transaction amount validation.
- SQLite stays the source of truth. Schema migration must retain every existing transaction, including its ID, amount, type, date, description, and creation time.
- Transaction ordering stays date, creation time, and ID descending.
- Deleting a transaction requires deliberate confirmation. Category rename/removal is deferred from 0.2; any future removal must preserve its transactions.
- Use installed React Native and navigation dependencies plus platform APIs; add no dependency for 0.2.
- Release APKs use the existing signing key. The first release on a new minor line must be tagged `v0.2.0`; later releases on that line increment the patch version.
- For every release to `main`, review and update affected GitHub wiki pages and verify the published guidance.

## Planning Calls to Review

These are concrete recommendations for review, not decisions already made by the product owner.

- Seed expense categories: Food, Transport, Home, Bills, Health, Shopping, Entertainment, Other. Seed income categories: Salary, Business, Gift, Other.
- A category belongs to one transaction type. Custom category names are unique without regard to case within that type.
- Category rename/removal is outside 0.2. If later added, built-ins stay protected and removal preserves linked transactions.
- The dashboard shows lifetime net balance (all income minus all expenses), current-calendar-month income and expense totals, and current-month expenses by category. The month uses the device's local calendar date.
- Existing 0.1 transactions migrate to the matching type's `Other` category. Users can then recategorize them by editing.

## Review Focus

- A v1 database migration fails partway: the original transactions and schema version remain intact. Test transactional rollback in `tests/schema.test.ts`.
- A category is missing or has the wrong type for a transaction: add and edit reject it without changing data. Test in `tests/transactionStorage.test.ts`.
- A date filter starts or ends on a transaction date: both bounds are inclusive and combined filters return only matching entries. Test in `tests/transactionFilters.test.ts`.
- Multiple valid amounts sum beyond JavaScript's safe integer range: the dashboard must not display a rounded financial total. Test in a new `tests/summaries.test.ts`.
- A custom category contains SQL-significant punctuation: it is stored as literal text without changing schema or other rows. Test in `tests/categoryStorage.test.ts`.

## Self-review

- The plan covers each 0.2 roadmap item: built-in and custom categories, transaction editing/deletion, history filters, a balance and spending dashboard, safe local migration, and release delivery.
- 0.3 budgets, 0.4 backups, and connected services remain out of scope.
- User-visible category list and dashboard periods are concrete recommendations for review. Category rename/removal is explicitly deferred from 0.2.
- The 0.2.0 versioning gap is included because the current workflow's patch-only calculation would otherwise produce `0.2.1` for a new `0.2.0` source line.
- Data migration, category/type validation, date boundaries, and safe integer totals each have an owning test in the plan.
